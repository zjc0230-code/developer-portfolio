## 第 5 页：核心技术突破 — "计划-填充"两阶段编排

**页面内容：**

标题："计划-填充"两阶段流式编排架构

左右对比布局：

左侧：传统串行流程（❌）
```
文本生成→语音合成→表情生成→动作生成
端到端延迟：> 1000ms
同步性差，各模态独立生成
```

右侧：我们的方案（✅）
```
第一阶段（0-50ms）：语义计划
    └─ 大模型快速生成结构化计划（核心内容+情感基调+表情动作需求+语音参数）

第二阶段（50-180ms）：并行填充
    ├─ 文本生成模块 ─┐
    ├─ 语音合成模块 ─┼─ 并行流式生成
    ├─ 表情生成模块 ─┤   基于同一语义计划
    └─ 动作生成模块 ─┘   天然同步

端到端延迟：< 180ms
同步误差：< 40ms
```

底部标注关键数据：
- 延迟从 1 秒+ 降至 180ms 以内
- 音视频同步误差 < 40ms
- 支持所有模态边生成边展示

**口述要点：**

这是整个项目最核心的技术创新。传统做法的根本问题是——所有模态串行生成，一个等一个，延迟叠加。我们的创新是：先让大模型花 50ms 生成一个"语义计划"（一个结构化的 JSON，几十个 token），这个计划定义了所有模态的共同目标。然后所有模态基于同一个计划并行生成。这样既保证了低延迟，又天然解决了同步性问题，因为大家的目标是一致的。而且容错性高——某个模态失败了，其他模态可以正常返回，失败的模态用默认值兜底。

## 第 6 页：核心技术突破 — 成本优化体系

**页面内容：**

标题：系统性推理成本优化 — 成本降低 62%

四个优化维度（图标+数据）：

1. 流式生成 + 动态批处理（vLLM + PagedAttention）
   GPU 内存利用率：25% → 65%，吞吐量提升 2-3 倍

2. 模型量化（AWQ 4bit + 混合精度）
   模型大小减少 75%，推理速度提升 2 倍，精度损失可忽略

3. 多级缓存机制
   L1 内存缓存（1小时，命中率 40%）→ L2 Redis 缓存（1天，命中率 25%）→ L3 向量缓存（语义相似，命中率 15%）
   总计减少约 80% 的模型调用

4. 智能模型路由
   简单请求→小模型(1.8B) · 复杂请求→大模型(7B) · 付费用户→专用实例
   在保证服务质量的前提下最大化降本

底部：总成果
推理成本降低 62%，年节省云资源成本 2800 万+

**口述要点：**

推理成本是 AI 数字人规模化部署的最大障碍。我们不是单点优化，而是从四个维度系统性地降低成本。重点讲一下缓存——大模型推理最贵的是重复计算，我们设计了三级缓存，效果非常好，80% 的调用被缓存命中。智能路由的核心思路是"好钢用在刀刃上"——不是所有请求都需要最强的模型，通过分层服务获得最优性价比。这个思路对面试官会有共鸣，这是真正的架构能力而不是算法能力。

## 第 7 页：核心技术突破 — 分层记忆与人设一致性

**页面内容：**

标题：四层分层记忆系统 + 人设校验机制

四层记忆架构图：

```
┌──────────────────────────────┐
│ L0：人设记忆层（永久）         │ ← 注入每次对话
│ 角色设定 · 背景故事 · 性格 · 风格 │    保证人设一致性
├──────────────────────────────┤
│ L1：长期记忆层（月度）         │ ← 自动提取用户认知
│ 用户档案 · 偏好 · 重要事件 · 关系 │    跨会话延续
├──────────────────────────────┤
│ L2：中期记忆层（周度）         │ ← 定期压缩整理
│ 会话摘要 · 任务状态 · 情绪 · 历史 │
├──────────────────────────────┤
│ L3：短期记忆层（会话）         │ ← 超限自动摘要
│ 当前上下文 · 实时状态 · 缓存     │
└──────────────────────────────┘
```

右侧：人设校验机制
AI 生成回复 → 人设校验模型 → 通过？→ 输出
                              ↓ 不通过
                         重新生成 / 兜底回复

**口述要点：**

记忆系统是 AI 数字人的"灵魂"。四层记忆模拟人类的记忆机制：永久不变的"我是谁"（人设层）、长期累积的"我对你的了解"、最近几周的"最近发生的事"、当前这个会话的"我们在聊什么"。设计上的巧思：不是所有对话都值得记，需要区分重要信息和无关信息。人设校验机制是一个安全网——大模型经常会"人设崩塌"，我们的做法是每次输出前用一个小模型做一次人设审查，不符合角色的就打回去重来。这套设计确保了 NPC 不管聊多久，始终是"它自己"。
