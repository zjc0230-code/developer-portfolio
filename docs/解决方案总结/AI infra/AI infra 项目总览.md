## 1. 格局

AI 基础设施（AI Infra）正从「模型训练时代的附属品」演变为「AI 应用规模化落地的核心瓶颈」。2024–2026 年行业格局三大变化：

**从模型为中心到应用为中心。** 2024 年之前，AI Infra 主要服务模型训练（GPU 集群、分布式训练框架、数据标注平台）。2025 年起，大模型推理成本下降 10 倍以上（以 DeepSeek V3/R1 为代表），应用层爆发，推理平台、模型网关、Agent 编排成为新的基础设施主战场。

**从单点工具到全栈平台。** 企业不再满足于"买个 GPU 服务器跑模型"，而是需要从模型接入、RAG 知识库、Prompt 管理、安全合规到成本控制的全链路平台。MCP（Model Context Protocol）等标准化协议的出现，加速了模型服务层的平台化。

**从技术尝鲜到 ROI 驱动。** 2025 年下半年起，企业对 AI 的投入从"先做再说"转向严格的 ROI 评估。GPU 利用率、token 成本、推理延迟、交付周期等指标成为 AI Infra 的核心 KPI。行业共识：谁能把 AI 应用的开发成本降下来、推理效率提上去，谁就掌握下一个十年的基础设施话语权。

在这一格局下，我的 AI Infra 实践覆盖了三条关键路径：**推理平台化**（AI 短剧生成平台）、**模型服务中间件**（MCP 上下文服务）、**MLOps 与开发者体验**（AI 营销工作流平台），形成了从底层资源调度到上层应用交付的完整能力闭环。

## 2. 挑战

AI Infra 领域的核心矛盾：**AI 应用需求爆发式增长 vs 基础设施成熟度严重滞后**。

### 2.1 推理侧挑战

| 挑战 | 现状 | 影响 |
|------|------|------|
| GPU 利用率低 | 行业平均 30–50%，闲置严重 | 推理成本居高不下，阻碍规模化 |
| 任务调度复杂 | 长任务（视频生成）vs 短任务（对话）混部 | 资源争抢、排队延迟 |
| 多模态流水线 | 文本/图像/视频/音频多阶段依赖 | 流程编排复杂，断点续传困难 |
| 模型版本管理 | 模型迭代快（周级），回滚需求频繁 | A/B 测试、灰度发布缺乏标准化 |

### 2.2 模型服务侧挑战

| 挑战 | 现状 | 影响 |
|------|------|------|
| 模型碎片化 | 不同业务用不同模型（GPT/Claude/混元/开源） | 接入成本高、切换困难 |
| 上下文管理 | 长对话 token 消耗指数增长 | 成本失控、响应变慢 |
| 安全合规 | 内容审核、数据隔离、海外合规 | 多套审核体系，维护成本高 |
| 多租户隔离 | 不同业务共享模型服务 | 资源抢占、数据泄露风险 |

### 2.3 开发者体验侧挑战

| 挑战 | 现状 | 影响 |
|------|------|------|
| AI 应用开发门槛高 | Prompt 工程、RAG、Agent 编排都需要专业能力 | 业务团队依赖 AI 团队，交付慢 |
| 工具链不统一 | 每个项目自建工具，重复造轮子 | 维护成本高、质量参差 |
| 从 Demo 到生产差距大 | 原型容易上线难（监控、降级、灰度） | 大量 AI 项目停留在 POC 阶段 |

### 3.2 方法论：AI Infra 三阶段成熟度模型

```
阶段 1：可用（Ad-hoc）
├── 单模型接入、手工部署、无监控
├── 交付周期：周级
└── 适用：POC 验证

阶段 2：可控（Platformized）      ← 当前主攻方向
├── 统一模型网关、标准化接入、基础监控
├── 交付周期：天级
└── 适用：多业务共享、中等规模

阶段 3：自愈（Autonomous）
├── 自适应调度、自动扩缩容、智能排障
├── 交付周期：小时级
└── 适用：大规模、高可用生产环境
```

核心方法论：**场景驱动、分层解耦、先通后优**。不做大而全的"AI 中台"，而是从最痛的场景（GPU 调度、模型接入、工作流编排）切入，逐步平台化。

## 5. 项目深度解析

### 5.1 AI 短剧生成平台

**定位：** 推理平台 + 任务调度 + GPU 资源管理

**业务场景：** 支持文本→图像→视频的多阶段 AI 内容生成流水线，面向短剧、广告素材等场景。

**核心架构决策：**

| 决策点 | 方案 | 备选与取舍 |
|--------|------|------------|
| 流水线编排 | 事件驱动（异步消息 + 状态机） | 不用 DAG 调度器——短剧生成步骤固定，事件驱动更轻量 |
| GPU 调度 | 基于 K8s Device Plugin + 自定义调度器 | 不用 Volcano——场景简单，自研调度器更灵活 |
| 断点续传 | 任务状态持久化 + Checkpoint 机制 | 每个阶段完成后写入状态存储，失败从断点恢复而非重跑全流程 |
| 利用率优化 | 任务合批（Batching）+ 分时复用 | 分析任务 GPU 显存需求，小任务合并到同一 GPU，提升利用率 28%→72% |

**关键技术挑战与解法：**

1. **多模态流水线的容错设计。** 短剧生成涉及文本模型、图像模型、视频模型多个异构推理任务，任一环节失败会导致整条流水线作废。解法：每阶段独立状态管理 + 自动重试 + 死信队列兜底，任务成功率从 85% 提升至 99%+。

2. **GPU 利用率从 28% 到 72%。** 初期 GPU 大量闲置——推理请求波峰波谷明显，且不同模型对 GPU 需求差异大。解法：① 基于历史负载的预测调度，提前预热/释放 GPU；② 小任务合批，在显存允许范围内并行处理；③ 非高峰时段自动缩容。

3. **长视频生成的中断恢复。** 视频生成任务可能运行数十分钟，GPU 节点故障会导致数十分钟的计算浪费。解法：阶段性 Checkpoint（每 5 分钟写一次中间结果），节点故障后在新节点从最近 Checkpoint 恢复，浪费控制在 5 分钟内。

### 5.2 MCP 模型上下文服务

**定位：** 模型服务中间件 + 向量数据库 + 多租户管理

**业务场景：** 为多个 AI 应用提供统一的模型接入层，屏蔽底层模型差异，管理上下文与知识库。

**核心架构决策：**

| 决策点 | 方案 | 备选与取舍 |
|--------|------|------------|
| 模型网关 | 统一 API 网关 + 适配器模式 | 不用 LangChain 等框架封装——网关层保持轻量，适配逻辑下沉到 Provider |
| 向量数据库 | Milvus 集群 + 多 Collection 隔离 | 不用单实例多租户——Collection 级别隔离更安全，运维复杂度可接受 |
| Token 管理 | 上下文窗口动态管理 + 历史摘要 | 不用全量保留——长对话自动摘要压缩，token 消耗 -30% |
| 标准化接口 | MCP 协议 + 自定义扩展 | 采用 MCP 标准协议降低集成成本，私有扩展处理腾讯特有需求 |

**关键技术挑战与解法：**

1. **多模型统一接入的复杂度。** 不同模型 API 差异大（OpenAI 格式 vs 混元格式 vs 开源模型），切换模型需改业务代码。解法：适配器模式 + 统一请求/响应 Schema，业务方只需改一个 model 参数即可切换。

2. **向量数据库的规模化运维。** 随着知识库增长（百万级向量），检索延迟上升、索引构建耗时。解法：① 分区索引（按知识库维度分区）；② 增量索引（新增文档增量更新，不定时全量重建）；③ 检索缓存（热点查询结果缓存，命中率 40%+）。

3. **上下文成本的精细化控制。** 多轮对话中 token 消耗指数增长，成本难以预估。解法：① 滑动窗口 + 智能摘要（超过窗口的历史对话自动压缩为摘要）；② 按用户/业务维度的 token 用量统计与告警；③ 成本归因到项目级。

### 5.3 AI 营销工作流平台

**定位：** MLOps + 开发者体验 + 低代码平台

**业务场景：** 让业务团队（运营、营销）能自助搭建 AI 驱动的营销工作流，降低 AI 应用开发门槛。

**核心架构决策：**

| 决策点 | 方案 | 备选与取舍 |
|--------|------|------------|
| 工作流引擎 | 自研轻量引擎 + 可视化编排 | 不用 Temporal/Cadence——营销场景流程简单，重量级引擎过重 |
| 低代码方式 | 拖拽式编排 + 模板市场 | 模板优先——先提供 10+ 场景模板，降低上手门槛 |
| AI 能力封装 | 原子化能力节点（文案生成/图片生成/数据分析） | 每个 AI 能力封装为标准节点，输入输出 Schema 标准化 |
| 监控与治理 | 全链路执行追踪 + 成本看板 | 每次工作流执行记录完整链路，支持成本/效果回溯 |

**关键技术挑战与解法：**

1. **AI 能力的标准化封装。** 不同 AI 能力（文案、图片、分析）输入输出差异大，编排时需要理解每个节点的细节。解法：定义标准节点协议（输入 Schema + 输出 Schema + 错误码），编排时只需关注数据流转，无需关心实现细节。

2. **从内部工具到可复用产品。** 初期为单个营销场景定制开发，无法复用。解法：① 抽象通用节点（条件判断、数据查询、消息推送等）；② 建立模板市场，新场景从模板改而非从零开发；③ 节点复用率达到 60%+。

3. **跨部门需求对接的标准化。** 业务方需求描述模糊（"帮我做一个 AI 营销工具"），返工率高。解法：建立需求模板（场景描述 → 输入数据 → 期望输出 → 效果指标），需求澄清时间从 3 天降至半天。

## 10. 高频问题与标准答案

> 面试/技术交流中针对 AI Infra 方向的高频问题及建议回答框架。每条回答保持"核心思路 + 回答要点"的结构，便于快速回顾。

### 10.1 技术与架构类

**Q: 你怎么设计一个支持 1000 并发的大模型推理平台？**

核心思路：分层架构 + 流量调度 + 弹性伸缩 + 容错。

回答要点：模型网关层做统一接入、负载均衡、限流、降级；推理引擎层 vLLM 与 TensorRT-LLM 混合部署，按场景选择最优引擎；资源调度层基于 K8s + Volcano 做 GPU 拓扑感知调度与弹性伸缩；存储层做模型缓存加速冷启动、向量数据库支撑 RAG；监控告警层覆盖推理延迟、GPU 利用率、token 消耗、错误率。

**Q: 你怎么优化 GPU 资源利用率？**

核心思路：从调度、批处理、混部、弹性四个维度切入。

回答要点：动态批处理和连续批处理最大化单 GPU 吞吐；GPU 共享技术（vGPU/MIG）支持多任务隔离混跑；训练和推理任务混部填谷削峰；离线任务和在线任务错峰调度；基于负载指标的弹性伸缩；闲置资源定时回收。实践中 GPU 利用率从 28% 提升至 72%。

**Q: 你怎么解决大模型幻觉问题？**

核心思路：从数据、模型、推理三个层面分层防御。

回答要点：RAG 检索增强生成是当前最有效的手段，将模型输出锚定在可信知识库上；引用溯源让用户可追溯每条结论的来源；事实校验层对关键输出做二次验证；多 Agent 交叉验证——多个 Agent 独立回答后投票；针对特定领域的微调可降低幻觉率；Prompt 工程约束输出格式和范围。实践中智能客服准确率做到 94%。

### 10.2 管理与决策类

**Q: 你怎么搭建和管理 AI Infra 团队？**

回答要点：按技术方向分工——推理平台、模型训练、平台工程、数据工程四条线；明确每个成员的职责、产出标准和成长路径（初级→独立负责→技术专家）；建立技术评审机制（设计方案评审、代码规范、上线 Checklist）；鼓励技术分享（双周分享会）和创新（20% 自由探索时间）。初期 3–5 人即可启动，优先招全栈能力强的工程师。

**Q: 一个技术问题，团队成员有不同的方案，你怎么决策？**

回答要点：第一步，明确业务目标和约束条件（时间、成本、人力），这是决策的锚点；第二步，让每个成员充分表达观点，确保不同方案被完整理解而非仓促否决；第三步，从可行性、风险、长期维护成本、团队能力匹配度四个维度评估每个方案；第四步，做出决策并清晰说明理由——让未被选中方案的人也理解为什么；第五步，事后复盘，验证决策是否正确，沉淀为团队经验。

**Q: 你怎么平衡技术先进性和业务落地？**

回答要点：业务优先，技术服务于业务目标——避免为技术而技术；对核心技术（如推理引擎、模型网关）适当超前投入，建立护城河；对非核心技术优先使用成熟的开源方案，减少重复造轮子；小步快跑策略——用最快速度拿出可用的 MVP，快速验证业务价值，然后逐步迭代优化。一句话总结：用 80% 的成熟方案解决 80% 的问题，用 20% 的创新方案建立差异化优势。

### 10.3 压力与陷阱类

**Q: 你没有大规模分布式训练经验，怎么胜任这个岗位？**

标准答案："我确实没有管理过千卡级训练集群的经验，但我有 7 年分布式系统的架构经验。分布式训练本质上还是分布式系统——数据一致性、容错、调度这些问题都是相通的。我之前做过推理平台的 GPU 调度和性能优化，对 GPU 的工作原理非常了解。而且我学习能力很强，之前的 MCP 服务、AI 短剧平台都是从零开始学习并落地的。我相信给我 1–2 个月的时间，完全可以上手分布式训练的相关工作。"
