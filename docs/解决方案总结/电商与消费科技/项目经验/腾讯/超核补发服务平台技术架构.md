# 超核补发服务平台

| 字段 | 内容 |
|------|------|
| **角色** | 技术负责人 / 核心架构 |
| **周期** | 持续维护 |
| **产业** | [电商与消费科技](../../行业解决方案.md) |

## 一句话

超核**道具/权益补发中台**：申请 → 审批（按需）→ 幂等发放 → 对账审计，与商城、活动共用身份校验，降低误发与重复发放资损。

---

## 情境（Situation）

- 活动、客服、运营存在高频补发诉求；各系统自建接口导致**重复发放、错发、难审计**。
- 发放对象须与尊享商城、活动中台的**游戏角色/账号**一致，否则引发客诉与资损。

## 任务（Task）

- 统一补发链路与服务契约，替代零散脚本与人工台账。
- 建设监控、告警与全量操作审计，满足合规复盘。
- 与交易中台**零资损**治理口径对齐（见 [01-交易中台](../../技术方案/01-交易中台与云上大促.md)）。

## 行动（Action）

### 架构

```
运营 / 客服 / 活动系统
        ▼
┌───────────────────┐
│  补发网关 / API     │ 鉴权、限流、幂等键
└─────────┬─────────┘
          ▼
┌───────────────────┐
│  补发编排服务       │ 规则引擎、批次、重试、死信
└─────────┬─────────┘
          ▼
┌─────────┬─────────┐
│ 游戏发货 │ 账务 / 审计日志 │
└─────────┴─────────┘
```

### 治理要点

| 能力 | 说明 |
|------|------|
| 幂等 | 申请单唯一 ID + 发货去重，防重复提交与重试双发 |
| 身份 | 复用商城/活动中台角色校验，避免跨系统 ID 不一致 |
| 审批 | 高额/批量补发可走审批流，留痕可追责 |
| 对账 | 与游戏发货回执对账，失败入重试或人工队列 |
| 监控 | 失败率、积压、异常发放率分级告警 |

### 系统集成

- **商城：** 共享用户/角色模型（[尊享商城](2020-2024_尊享商城.md)）。
- **活动：** 奖励发放可路由至补发平台统一执行（[活动中台](2019-2026_超核活动中台_超核基地.md)）。

## 结果（Result）

- 补发能力**平台化**，业务线减少自建发放逻辑与运维面。
- 发放链路**可追溯**（操作人、原因、工单/活动 ID），支撑运营与客服复盘。
- 与「3 年零资损」商城治理同一安全文化；**内部发放量级与成功率**待报表回填（见 [改进建议](../../../改进建议.md) P1）。

## 面试话术（30 秒）

「补发本质是**写路径上的交易**：我把发放做成带幂等、审批和审计的中台，和商城共用身份校验，避免客服和活动各搞一套接口导致双发。」

## 技术栈

Golang · TRPC · MySQL · Redis · 幂等 · 审计日志 · 业务监控
